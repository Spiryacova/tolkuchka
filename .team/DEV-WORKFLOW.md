# DEV-WORKFLOW.md — Процесс разработки фич с использованием скиллов

Как команда из 2 разработчиков проектирует и реализует каждую фичу/страницу. Работает вместе с `DESIGN-SYSTEM.md`, `TOLKUCHKA-PLAN.md`, `GIT-WORKFLOW.md`, `CI-CD.md`.

---

## 1. Общая схема

```
Шаг 0. Дизайн-система (создана один раз, см. DESIGN-SYSTEM.md)
        ↓
Шаг 1. Проектирование экрана через скиллы (JTBD → CRO → сущности + компоненты → refactoring-ui)
        ↓  выход: артефакт проектирования + тех. каркас страницы (раздел 3)
Шаг 2. Сверка с дизайн-системой (единообразие) + карта сущностей (есть / нет)
        ↓  выход: список недостающих сущностей
Шаг 3. Согласование реализации (варианты: добавить в Prisma / переиспользовать / отложить)
        ↓
Шаг 4. Реализация по плану (server/api, Prisma, Pinia, SSR/SEO) → PR по GIT-WORKFLOW.md
        ↓
Шаг 5. Финальный контроль (typecheck, lint, проверка по DESIGN-SYSTEM.md)
```

**Разделение ответственности:**
- **Скиллы (Шаг 1)** — решают «как выглядит и ведёт себя интерфейс» (UX, визуал, JTBD)
- **План и агент (Шаги 3–4)** — решают «как это работает с реальными данными» (Prisma, API, Pinia, SSR)

---

## 2. Правило сложности

Не каждый экран требует полного цикла. Определяем уровень перед Шагом 1:

| Уровень | Что попадает | Цикл скиллов |
|---------|--------------|--------------|
| **Сложный** | Корзина, checkout, личный кабинет, панель продавца, каталог с фильтрами | Полный: JTBD → CRO → сущности + компоненты → refactoring-ui |
| **Средний** | Карточка товара, история заказов, формы | JTBD (кратко) → refactoring-ui |
| **Простой** | Кнопка, бейдж, хедер, мелкие элементы | Без скиллов: сразу по дизайн-системе + карте Nuxt UI |

**Где уместен CRO:** CRO прогоняется только на конверсионных страницах — лендинги (`/`, `/seller`), каталог, карточка товара, корзина, checkout. Внутренние инструменты (кабинет продавца, `account`) CRO не проходят: для них JTBD + UX (design-everyday-things) + refactoring-ui.

**Порядок работы:**
1. Определить уровень сложности экрана (по таблице)
2. Прогнать скиллы по соответствующему циклу
3. Выход — артефакт проектирования (раздел 3)

---

## 3. Артефакт проектирования (выход Шага 1)

После прогона скиллов фиксируем **формализованный результат** — его передаём на Шаг 2–4. Шаблон:

```markdown
## Экран: [название страницы / компонента]
Уровень: сложный / средний / простой

### Блоки интерфейса
1. [блок] — [назначение, приоритет]
2. ...

### UX-правила
- [как ведёт себя интерфейс при действиях: клики, фидбеки, защита от ошибок]

### Компоненты Nuxt UI
- [UCard, UDataTable, UBadge ...] — для каких блоков

### Затрагиваемые сущности
- ✅ уже есть в проекте: [User, Order, ...]
- ❌ нет в проекте: [Address, ...]

### Технический каркас
- **Layout:** default / dashboard; **middleware:** auth / seller / guest / нет
- **Рендеринг:** SSR / ISR / prerender; **SEO:** перечень `useSeoMeta`-тегов
- **Состояния:** loading (USkeleton/USpinner) / empty / error
- **Внутренние ссылки:** откуда на страницу приходят, куда она ведёт (breadcrumbs, CTA, контекстные)

### Сверка с дизайн-системой
- [соответствует / отклонения + замечания]
```

## 4. Шаг 2 — Карта сущностей

Сверяем блоки экрана с моделью данных проекта (Prisma schema в `TOLKUCHKA-PLAN.md`):

| Блок экрана | Нужная сущность | В проекте? |
|-------------|-----------------|------------|
| Профиль покупателя | User (имя, email, аватар) | ✅ есть |
| История заказов | Order, OrderItem | ✅ есть |
| Адреса доставки | Address | ❌ нет |

**Результат Шага 2** — список недостающих сущностей с обоснованием «для чего нужны».

---

## 5. Шаг 3 — Согласование недостающих сущностей

Для каждой ❌ сущности агент/напарник предлагает **варианты** — команда выбирает:

| Вариант | Когда | Пример |
|---------|-------|--------|
| **Добавить в Prisma** | Сущность критична и будет использоваться | Address → новая модель + миграция |
| **Переиспользовать** | Есть подходящее хранилище | «Адрес» → поле `shipping_address` (jsonb) у Order |
| **Отложить / упростить** | Не критично для MVP | Вишлист → в бэклог |

**Решение фиксируется в плане** (добавляется задача в спринт или «на потом»).

---

## 6. Шаг 4 — Реализация по плану

Когда проектирование согласовано — реализация идёт **по основному плану** (`TOLKUCHKA-PLAN.md`), с учётом:

- **Бэкенд:** server/api маршруты → Prisma запросы (по схемам из плана)
- **Состояние:** Pinia store (auth, cart, products, seller) для межстраничных данных
- **Данные в UI:** `useAsyncData`/`useFetch` (SSR), `useColorMode` (тема)
- **SEO:** `useHead`/`useSeoMeta` на публичных страницах
- **Процесс:** ветка → PR → ревью по `GIT-WORKFLOW.md`, CI зелёный

---

## 7. Шаг 5 — Финальный контроль перед PR

Перед мержем каждой фичи:

1. `npm run lint && npm run typecheck` — зелёные
2. Сверка по чек-листу дизайн-системы (раздел 9 в `DESIGN-SYSTEM.md`)
3. Проверка: SSR/ISR применён, SEO-теги на месте, нет секретов в клиентском коде
4. Loading/empty/error состояния есть
5. Тёмная тема работает (проверить ключевые страницы в обоих режимах)

## 8. Роли в процессе

| Шаг | Кто ведёт | Участвует |
|-----|-----------|-----------|
| 1. Проектирование | Разработчик (с AI-агентом/скиллами) | Оба обсуждают результат |
| 2. Карта сущностей | Разработчик + AI-агент | Сверка с планом |
| 3. Согласование | Оба разработчика | AI-агент предлагает варианты |
| 4. Реализация | Назначенный по плану (Dev 1/Dev 2) | Ревьюер по PR |
| 5. Контроль | Ревьюер | CI автоматически |

---

## 9. Приоритет согласованности

Главная цель процесса — **единообразный дизайн**:

1. Новый экран обязан соответствовать `DESIGN-SYSTEM.md` (иерархия, цвета, типографика, отступы)
2. **Компоненты Nuxt UI не оборачиваются:** примитивы используются напрямую (`<UButton>`, `<UCard>`), кастомизация — только через `app.config.ts` (`ui.<component>`, `defaultVariants`). Свои компоненты создаются только для доменных композитов (`ProductCard`, `CartItem`), которых нет в карте Nuxt UI
3. Любое изменение палитры/токенов — только через правку дизайн-системы, не локально
4. Если дизайн-система не покрывает случай — дополняем её документ (правка проходит через PR)
